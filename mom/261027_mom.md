## 결정 사항

보드별 역할을 나누고, API 명세의 작성 방식과 명명 규칙을 정했다. 데이터 형식은 JSON 문자열로 한다.

**역할 분담**

보드는 통신, 차량, 레이더 3개이고 팀은 3명이다. 통신 보드 담당이 둘이면 범위가 겹치므로, 보드가 아닌 기능 단위로 나눴다.

| 담당 | 범위 |
| --- | --- |
| 조이스틱·버튼·PC | 통신 보드의 조이스틱과 버튼 입력, PC 프로그램(로그 출력과 화면) |
| 블루투스 | 통신 보드 ↔ 차량 보드 블루투스 송수신 |
| 차량·레이더 | 차량(모터) 보드와 레이더 보드 |

- 담당자: 조이스틱·버튼·PC는 유지호, 블루투스는 장문수, 차량·레이더는 김인규가 맡는다. (녹취에서 이름이 명확하지 않아 확인이 필요하다.)
- 통신 보드는 `main`을 그대로 두고, 각자 헤더와 C 파일을 새로 만들어 모듈화한 뒤 `main`에서 호출한다.
- 블루투스는 다뤄 본 사람이 없고 핀맵과 데이터시트를 직접 확인해야 하므로, 가장 어려운 파트로 본다.

**API 명세 방식**

- 명세서는 엑셀로 작성한다. 시트는 역할별로 나눈다.
- 대분류(예: 모터, 이동)와 소분류에 API를 적는다.
- 컬럼은 API명(함수명), 데이터, 비고, 에러 코드, 예시 값이다. 예시 값은 `int 1`, `direction: up`처럼 옆에 주석을 붙인다.
- 데이터 타입과 상세 구조는 지금 정하지 않는다. 기능을 먼저 구현하는 쪽이 명세를 먼저 적고, 불가능하면 대화하며 바꾼다.
- 모든 API에는 응답이 있다. 요청을 받았는지, 제대로 움직였는지 확인할 수 있어야 한다. ACK/NAK 방식도 언급됐다.

**데이터 형식과 이름 규칙**

- 통신 값은 문자열로 주고받고, 받는 쪽에서 JSON 형태로 파싱해 **구조체**로 넘긴다.
- 함수명은 **소문자 스네이크 케이스**로 통일한다. 카멜 케이스와 섞지 않는다.
- 함수명은 `보내는 주체_대상_동사_명사` 순서를 기본으로 한다.
- 보드별 접두어는 다음과 같다.

| 대상 | 이름 |
| --- | --- |
| PC | `client` |
| 통신 보드(조이스틱) | `route` |
| 블루투스 | `bt` |
| 차량(모터) 보드 | `vehicle` |
| 레이더 보드 | `radar` |

- 예시: `route_bt_send_...`처럼 주체와 대상을 앞에 붙인다.
- 호출 규칙: 수신한 쪽이 구현자가 정한 API 함수에 데이터를 던지면, 함수가 그 데이터를 처리한다.

**레이더 데이터**

- 레이더 보드가 처리해서 **각도(도)와 거리(cm)**만 보낸다. 받는 쪽은 주기를 신경 쓰지 않고, 데이터가 오면 바로 처리한다.
- 각도는 정면을 0°로 하고 −n°에서 +n°까지 쓴다.
- 서보 모터의 현재 각도는 센서가 아니라 보낸 회전 명령을 기준으로 추정한다. MVP라서 정확도는 포기한다.
- 정확한 각도 범위와 서보 모터의 출력값은 직접 구동해 보고 확정한다.

## 협업 기록

데이터 전송 시점, 가공 위치, 확장성에 대한 이견을 근거를 들어 조율했다.

### 1. 데이터 가공 위치: 원본 전송 vs 가공 후 전송

- **쟁점**: 레이더 값을 원본으로 보낼지, 거리와 각도로 가공해서 보낼지
- **원본 전송 근거**: 활용 방법이 여러 가지이므로 원본을 해석하는 일은 PC에서 하는 편이 낫다.
- **가공 전송 근거**: 거리를 깔끔하게 보내는 편이 통신에 적합하다. 레이더 보드가 센서를 직접 다루므로 그쪽에서 처리하는 편이 효율적이다.
- **결론**: 레이더 보드에서 가공해 센티미터와 각도만 보낸다. 중간 보드는 그대로 전달하고, 통신 보드에서 PC로 보낼 때만 필요하면 파싱한다.

### 2. 명세 범위: 지금 확정 vs 구현하며 확정

- **쟁점**: 속도, 센서 교체 가능성처럼 확장성까지 명세에 넣을지
- **확정 의견**: 현재 속도를 하드코딩했지만 수정 가능성이 있으므로 조이스틱 전송 값에 속도 필드가 있어야 한다.
- **구현 중 확정 의견**
  - 확장성은 구현자의 코드에 따라 달라지므로 지금 정할 수 없다.
  - 값의 범위나 주기는 정하지 않아도 보내는 쪽이 정한 값을 받으면 된다.
  - 데이터 형식과 키 이름만 맞으면 나머지는 AI가 처리할 수 있다.
- **결론**: 필요한 값은 키 이름 기준으로 먼저 정하고, 속도 같은 확장 항목은 후순위로 두며 구현하며 반영한다.

## 기타 논의

- **조이스틱 전송 방식**: 1바이트를 비트 마스크로 쓰는 안이 나왔다. 최상위 비트는 시동 ON/OFF, 나머지 4비트는 상하좌우 방향이다. 문자열 방식이 더 간단하다는 의견과 함께 구현 중에 확정한다.
- **명칭**: 프로젝트명이 "무빙 터렛"이라 헷갈릴 수 있으므로 레이더 보드는 `radar`로 통일하고 "터렛"으로 부르지 않는다.
- **PC 통신**: PC 한 대와 보드 한 대가 1:1로 UART 연결된다. PC에서 받은 데이터는 AI로 확인한 뒤 파싱 방식을 정한다.
- **로그 확인**: PC에서 로그를 보려면 로컬 환경에서 앱을 띄워야 한다.
