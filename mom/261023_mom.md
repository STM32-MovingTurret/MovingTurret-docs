## 결정 사항

MVP 범위, 개발 방법론(V 모델), 통신 구조를 정했다. 상세 기능 명세는 AI가 생성한 초안을 바탕으로 수정하며, 프로젝트명은 **STM32 무빙 터렛**으로 정했다.

**MVP 기능 (우선순위 순)**

1. **초음파 레이더**: 장애물 위치를 파악한다.
2. **조이스틱 이동**: 전진·후진·제자리 회전·정지를 제어한다.
3. **시동 ON/OFF(파킹 모드)**: 시동이 꺼진 상태에서는 조이스틱 입력을 무시한다. 스위치 하나와 상태 하나만 추가하면 되는 수준이라 MVP에 포함했다.
4. **보드 간 통신**: UART로 구현한다.
5. **PC 로그 출력**: 레이더 감지 결과를 PC에서 로그로 확인한다.

- **충돌 감지**는 우선순위에서 제외했다.
- **레이더 시각화(그림 그리기)**는 MVP 선택 항목으로 두었다. 로그만 받으면 나중에 그릴 수 있고, 임베디드보다 PC 쪽 작업이라는 점이 근거였다.
- **레이더 회전 범위**는 **180°**로 정했다. 명세서에도 180°로 적는다.
- **PC**는 제어 없이 수신해서 대시보드나 로그로 보여주기만 한다. 조이스틱 입력은 차량으로만 보낸다.
- **통신 두절 시 안전 정지**는 코드로 구현할 수 있어 비기능 요구사항 후보로 올렸다.

## 개발 방법론: V 모델

워터폴, 애자일, V 모델을 비교한 끝에 **V 모델**로 정했다. 근거는 협업 기록에 정리했다. 스터디 기준으로 지켜야 하는 절차는 아니지만 최대한 따르기로 했다.

## 시스템 구성

**최종 구조**

- 보드는 **통신 보드, 차량(모터) 보드, 레이더 보드** 3개다.
- 조이스틱과 버튼은 통신 보드에 빵판으로 연결한다. GPIO 입력을 통신 보드가 받아서 처리한다.
- **통신 보드 ↔ 차량 보드**는 블루투스(HC-05 마스터, HC-06 슬레이브)로 연결한다.
- **레이더 보드 → 차량 보드**는 UART로 보낸다.
- **통신 보드 ↔ PC**는 UART로 연결한다. 보드 빌드 때 쓰는 USB 케이블로 UART 통신도 되므로 추가 부품은 필요 없다.
- 레이더 값은 레이더 보드 → 차량 보드 → 통신 보드 → PC 순서로 단방향으로 올라간다.
- PC 쪽 레이더 시각화에는 초음파 거리뿐 아니라 **레이더가 바라보는 방향(서보 모터 각도)**도 함께 보내야 한다. 바퀴 2개와 서보 1개로 모터는 총 3개다.

**연결 방식 검토**

- 레이더 보드와 차량 보드를 합치는 것도 가능하지만, 보드 간 통신 경험을 위해 분리하기로 했다.
- 블루투스 모듈은 HC-05와 HC-06을 각각 갖고 있다. HC-05는 마스터 모드를 지원한다.
- 블루투스 동글은 다이소에서 약 5,000원에 살 수 있다.

**진행하면서 주의할 점**

- 보드 수가 늘어 배선이 복잡해진다. 전압이 불안정하거나 노이즈가 끼면 통신이 끊길 수 있다.
- 선이 길어지면 잡음이 늘어난다. 필요하면 CRC 같은 오류 검출을 패킷에 넣는다.
- 보드마다 클럭과 시리얼 통신 속도를 맞춰야 한다. 통신 보드는 PC와도 따로 통신하므로 타이머를 여러 개 써야 할 것 같다.
- `main`에 모두 작성하지 않고 모듈별로 헤더와 C 파일을 나눈다. 협업과 포트폴리오 완성도 모두에 유리하다.

## 협업 기록

개발 방법론, 통신 방식, 레이더 회전 범위, 레이더 시각화의 MVP 포함 여부는 근거를 들어 조율했다.

### 1. 개발 방법론: 워터폴 vs 애자일 vs V 모델

- **쟁점**: 어떤 개발 프로세스를 따를지
- **애자일 의견**
  - 기능을 하나씩 만들고 추가하는 방식이 낫다.
  - 워터폴은 처음에 모든 설계를 끝내야 하는데, 그만한 지식이 아직 없다.
- **애자일 반대 근거**
  - 기능을 추가할 때마다 계속 소통해야 하는데, 팀원들이 쓸 수 있는 시간은 주 3~6시간이다.
  - 방산처럼 명세가 중요한 분야에서는 V 모델을 많이 쓴다. 자동차 업계는 AUTOSAR 도입 이후 애자일을 쓴다는 의견도 나왔다.
- **워터폴·V 모델 근거**
  - 과제로 받은 문서 순서(요구사항 → 설계 → 구현 → 테스트)가 이미 워터폴에 맞춰져 있다.
  - 상세 기능은 AI로 정리할 수 있다.
  - 보드가 여러 개라 통합 단계에서 문제가 반드시 생긴다. 테스트로 올라가며 검증하는 구조가 필요하다.
- **결론**: V 모델로 결정했다. MVP를 먼저 구현하고, 후순위 기능은 같은 흐름으로 다시 돌린다.

### 2. 통신 방식: 유선 UART vs 블루투스

- **쟁점**: 조종기와 RC카, PC와 RC카를 무엇으로 연결할지
- **진행 과정**
  1. 처음에는 UART로 시작하자는 의견이 나왔다. 이미 해본 방식이고 설정이 간단하다.
  2. 이어서 중요한 것은 통신 방식이 아니라 통신해서 화면에 띄우는 것이라는 의견이 나와, 무선 통신은 향후 과제로 미루기로 했다.
  3. 하지만 조종기와 RC카, PC와 RC카까지 통신이 두 가지라 전부 선으로 하면 어렵다는 점이 지적됐다. PC 쪽은 블루투스가 낫다는 의견이 나왔다.
  4. 조종기를 별도 보드로 둘지, 통신 보드와 합칠지 논의했다. 합치면 조이스틱을 GPIO로 받아 처리할 수 있다.
  5. 조종기와 차량을 선으로 길게 연결하면 잡음과 꼬임이 문제다. 보드를 따라다니며 선을 들고 있는 방식은 비현실적이라는 의견이 나왔다.
  6. 통신 보드와 차량 보드는 블루투스로 연결하기로 정리했다. 모듈이 마스터/슬레이브로 한 쌍 있어 통신할 수 있다.
- **결론**: 최종 구조는 위의 시스템 구성을 따른다. 처음 구조와 달라져 혼선이 있었으므로, 그림으로 정리해서 팀 문서에 올린다.

### 3. 레이더 회전 범위: 180° vs 360°

- **쟁점**: 초음파 센서를 얼마나 회전시킬지
- **360° 근거**: 전방위 탐색이 가능하다. 직접 해보고 싶다는 의견도 있었다.
- **360° 반대 근거**: 센서 선이 꼬이지 않게 하려면 슬립링 같은 별도 부품이 필요하다. 공학적 난도가 높다.
- **180° 근거**
  - 차량 몸체가 부딪힐지 판단하려면 정면만 보면 애매하다. 장애물 크기를 알려면 좌우로 훑어야 하며, 180°면 충분하다.
  - 바퀴가 2개이고 제자리 회전을 하므로 이동 방향만 보면 된다.
  - AI가 생성한 명세서도 180°로 적혀 있다.
- **결론**: 180°로 확정했다. 360°는 추가 구현으로 남긴다.

### 4. 레이더 시각화: 필수 vs 선택

- **쟁점**: PC에 레이더 그림을 그리는 것을 MVP에 넣을지
- **필수 의견**: 초음파를 단 이유가 이를 출력하기 위해서다. 선택으로 두면 "왜 달았냐"는 질문에 답하기 어렵다.
- **선택 의견**
  - 로그만 받으면 그림은 나중에 그릴 수 있다. AI가 대시보드 코드를 만들어 줄 수 있다.
  - 임베디드보다 PC 쪽에 가까운 작업이다.
- **결론**: MVP는 로그 출력까지다. 시각화는 선택 항목으로 두고, 임의 데이터로 화면을 먼저 만들어 보고 통합할 때 검증한다.

## 기타 논의

- **개발 기간**: 남은 기간은 약 6주이고, 개발 기간은 따로 정해져 있지 않다. 바빠지기 전인 지금 최대한 빨리 끝내자고 했다.
- **일정**: 한 팀원은 다음 주부터 면접 준비로 참여가 어렵다. 해당 팀원은 명세까지 참여하기로 했다.
- **형상관리**: GitHub Organization을 만들어 팀 저장소를 옮긴다. 기존 저장소는 커밋 기록이 사라질 수 있으니, 기록을 유지하며 이전하는 방법을 확인한다.
- **AI 활용 기록**: AI로 개발하더라도 문제를 어떻게 접근하고 어떤 프롬프트로 해결했는지 기록한다. 코드는 한 번씩 읽고 흐름을 이해해야 면접에서 대답할 수 있다.
- **비기능 요구사항**: 정해진 기준이 없어 팀이 판단해야 하는 영역이다. 면접에서 근거를 물을 수 있으므로 미리 근거를 정리한다.
- **보드 간 API 명세**: 필요하다는 데 합의했다. 다음 회의에서 역할 분담과 함께 정한다.
- **PC 앱**: AI가 만들더라도 트러블슈팅과 유지보수는 사람이 해야 하므로 담당자가 필요하다.
